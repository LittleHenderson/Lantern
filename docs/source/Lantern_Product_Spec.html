01 · Executive summaryExecutive summary

Lantern maps every call path in a codebase, explains each piece in three registers, audits it with real security tooling, and grades how ready it is to ship. The output is evidence a builder can hand to a skeptical engineer.

A new class of builders ships software with AI assistance. They move fast, but they often can't explain what their code does, and they don't know what they don't know about security or deployment. Professional engineers notice, and the label "AI slop" sticks even when the work is sound.

Lantern closes that gap in four moves:

  1. Map. It parses Python and TypeScript/JavaScript repositories (then Rust and C++) into a single call graph, joins the frontend to the backend wherever one calls the other over HTTP, and renders it as an interactive flowchart. A path starts at a real entry point, such as a page, a button's click handler, an API route, main(), or a CLI command, and can run unbroken from the button to the database.
  2. Explain. Every function and module gets three explanations: a technical one, a plain-English one with analogies, and a mapped one where each everyday phrase is pinned to the exact technical term it stands for.
  3. Audit. Established static-analysis and dependency scanners find the security problems. The call graph tells you which findings are actually reachable. An LLM of the user's choosing explains each finding and drafts a fix, and a rescan verifies the fix.
  4. Prove. A Deployment Readiness Score and a shareable Evidence Report tie each claim to a specific commit and to the tool that produced it.
Two ways in

Cloud mode

Connect GitHub. A sandboxed worker clones the repo, analyzes it, and destroys the copy. Zero setup, works from any device.

Two ways in

Local agent mode

Run one binary on your own machine. Source never leaves it; only results are uploaded, with optional redaction. Model calls can stay local too.

The core design bet

Deterministic tools find facts; language models explain them. The call graph, the security findings, and the readiness checks come from parsers and scanners whose output is repeatable. Models never invent structure or vulnerabilities. They translate verified facts into language people can learn from. That separation is what makes the output credible to engineers.

02 · Problem and audienceProblem, audience, and positioning

AI tools let people build software faster than they can understand it. Lantern sells understanding, and the proof of it.

2.1The gap

An AI-assisted builder can produce a working app in a weekend. What they usually can't produce is an answer to the questions a reviewer asks: What calls this? What happens if this input is malicious? Where are the secrets? How does this run in production? What breaks under load? The criticism they get is often fair on the specifics, but it lands as dismissal of the whole person. Nothing on the market today turns "I built this" into "I understand this, and here's the evidence."

Most of these apps are full stack: a React or Next.js frontend, usually in TypeScript, talking to an API or a hosted database. Many of the holes engineers point to live exactly where the two halves meet: server secrets shipped in the browser bundle, API routes the frontend calls without any login check, database access rules switched off, and CORS left wide open. A reviewer's real question is usually "what happens when someone clicks this button?" Answering it means following one path across both halves, so Lantern treats the whole stack as one program.

2.2Who it's for

Primary

The AI-assisted builder

Ships real projects with AI coding tools. Self-taught or career-switching. Wants to learn what their code does and stop getting dismissed. Uses a phone and laptop interchangeably.

Job to be done: "Help me understand my code well enough to defend it, and fix what's indefensible."

Secondary

The reviewing engineer

Receives an Evidence Report from a builder, a contractor, or a junior teammate. Has five minutes. Trusts scanners more than claims.

Job to be done: "Show me, quickly and verifiably, whether this is safe to merge or deploy."

Secondary

The learner and educator

Students, bootcamps, and self-learners who use the Three-Lens view to climb from plain English to real terminology on codebases they care about.

Future

The small team lead

Onboards new hires onto an unfamiliar codebase and wants a living map plus a readiness gate in CI.

2.3Landscape

Positioning statement

For AI-assisted builders who get dismissed by engineers, Lantern is the code-understanding platform that turns a repository into a verified map, plain-English explanations, and a security and readiness report. Unlike AI explainers, every structural and security claim comes from deterministic tools and is traceable to a commit.

03 · PrinciplesProduct principles

These principles settle design arguments. When two good ideas conflict, the higher one wins.

PrincipleWhat it means in practice
1 · Facts from tools, words from modelsCall edges, findings, and readiness checks MUST come from deterministic analysis. Models MUST only explain, triage, and propose fixes, and their output is always labeled as model-generated.
2 · The user decides where code goesCloud mode and local mode are equal first-class paths. Every screen that sends data anywhere says exactly what is sent and to whom.
3 · Show confidence, never fake certaintyEvery edge and finding carries a confidence level. Dynamic languages produce uncertain graphs; Lantern says so instead of hiding it.
4 · Teach, don't just tellPlain language is a ramp toward real terminology, never a replacement for it. The mapped lens exists so learners graduate.
5 · Evidence must be verifiableReports are pinned to a commit hash, list the tools and versions used, and state what they do not prove.
6 · Practice what we preachLantern handles source code and API keys. It MUST pass its own audit and publish its security posture.
7 · Mobile is a real surfaceEvery core task, short of initial local-agent setup, works on a phone.
Tone guardrail

Lantern is on the builder's side but never flatters. A low readiness score is shown plainly, with the path to improve it. The report's credibility with engineers depends on it being honest with builders.

04 · FeaturesFeature overview

Six capabilities, each built on the one before it.

F1

Code Atlas

An interactive map of every function, method, and module, and who calls whom. Two views: a zoomable network overview, and a Flow view that lays out one entry point's call path as a top-down flowchart.

F2

Three-Lens explanations

Technical, Everyday, and Mapped explanations for every node, toggled instantly. The Mapped lens pairs each plain phrase with its technical twin, one-to-one.

F3

Security audit

Real scanners, reachability analysis over the call graph, model-written explanations in all three lenses, suggested fixes as diffs, and verification by rescan. Also proactive suggestions for security features the app lacks.

F4

Deployment readiness

A 0–100 score across ten categories, plus a systems-design advisor that recommends a deployment shape and generates starter files such as a Dockerfile, a CI workflow, and .env.example.

F5

Evidence Report

A shareable, commit-pinned report with a public link and PDF export, built for an engineer with five minutes.

F6

Model choice

Bring your own API key for any major provider, or run local models. Pick models per task, preview costs before a run, and compare two models' explanations side by side.

4.1Core user journey

  1. Connect. The user signs in on the PWA and chooses cloud mode (authorize the GitHub App on selected repos) or local mode (install the agent and pair it by scanning a QR code or entering a one-time code).
  2. Configure. They choose models for each task and see an estimated token cost for a full run. They choose a privacy level (Section 5.3).
  3. Analyze. Structural analysis and scanning run first and finish quickly. Explanations stream in afterward, entry points first. A push notification fires when the run completes.
  4. Explore. They open the Atlas at an entry point, follow the path, and toggle lenses on any node.
  5. Fix. They work down the findings and readiness checklist, apply suggested patches (cloud mode opens a pull request; local mode writes a patch file or applies it on confirmation), then re-run.
  6. Prove. They publish an Evidence Report and share the link.

05 · ArchitectureSystem architecture and the two access modes

One analysis engine, packaged as a single binary, runs in two places. That guarantees identical results whether the user picks cloud or local.

Figure 1. System overview. The same lantern agent binary performs analysis in both modes. In cloud mode it runs inside a disposable sandbox; in local mode it runs on the user's machine and sends only results.

5.1Cloud mode

Best for zero setup and for users who work mostly from a phone or tablet.

  • Access. A GitHub App with the narrowest permissions: read-only repository contents and metadata on repositories the user explicitly selects. Pull-request write permission is requested separately, only when the user first asks Lantern to open a fix PR.
  • Isolation. Each job runs in a fresh microVM (Firecracker or gVisor class) with no persistent disk, CPU and memory caps, a wall-clock limit, and egress restricted to the configured model endpoints.
  • Untrusted code. The worker never runs the user's build scripts or tests by default. This matters most for C++ (CMake configure steps execute code), Rust (build scripts and procedural macros execute code), and JavaScript (npm install runs package lifecycle scripts, so the worker never installs dependencies; it reads lockfiles instead). Section 6.3 covers the accuracy trade-off and the opt-in "sandboxed build" setting.
  • Retention. The clone is destroyed when the job ends. Only derived results persist: the graph, findings, scores, and explanations. Source snippets inside results are governed by the privacy level.

5.2Local agent mode

Best for private or proprietary code and for users who want model calls to stay on their own hardware.

  • Distribution. A single signed binary for macOS (Apple silicon and Intel), Linux (x86-64 and ARM64), and Windows. Install via Homebrew, a shell script with a published checksum, winget, or cargo install.
  • Pairing. lantern login shows a one-time code and QR code. The user approves it in the PWA, and the agent receives a device-scoped, revocable token.
  • Operation. lantern analyze runs once. lantern watch re-analyzes on file changes. The agent can also sit idle and accept "analyze now" requests triggered from the PWA, so a user on their phone can kick off a run on their home machine.
  • Model calls. Made directly from the agent using keys stored in the operating system's keychain, or sent to a local model server. In this mode Lantern's servers never see API keys or source.
  • Tooling. The agent uses language servers and scanners already installed on the machine when present, and offers to fetch pinned versions when they're missing.

5.3What leaves the machine: privacy levels

Both modes honor one setting that controls how much source-derived content is stored in Lantern's cloud. The PWA shows the active level on every analysis.

Be precise with users

Even in local mode, if the user chooses a cloud model provider, source code is sent to that provider to generate explanations. The UI MUST say this in plain words when a cloud model is selected, and MUST offer local models as the alternative. "Your code never leaves your computer" is only true with a local model.

Why the order is Python → TypeScript/JavaScript → Rust → C++

Python has the simplest toolchain and a large share of AI-built backends. TypeScript/JavaScript comes right after because most apps this audience ships are full stack, and a Python-only map leaves the frontend, often most of the code, invisible: on the FastAPI full-stack template, 10,000 of its 13,000 lines are TypeScript. Rust has excellent tooling and moderate difficulty. C++ is the hardest to analyze correctly and the riskiest to analyze safely in the cloud, so it ships last, with lessons learned from the rest.

6.4Full-stack tracing: the frontend-to-backend bridge

The signature output of a full-stack Lantern is one unbroken path through the whole app. Each language is parsed into the same graph, and then a bridge stage joins them: every HTTP call found in frontend code is matched to the backend route that answers it.

Figure 2b. One path from a button to the database, measured on the open-source FastAPI full-stack template in Phase 0.

What the bridge reads

  • Frontend calls: fetch, axios-style clients (api.get("/items")), and generated API clients that carry a url field. Template strings become path parameters, so `/items/${id}` matches /items/{id}.
  • Backend routes: every route entry point in the graph, from any language: FastAPI, Flask, and Django in Python; Next.js route handlers, Express, Hono, and Fastify in JavaScript.
  • Third-party APIs: calls that match no route stay on the map as External nodes with their host, so the user sees where data leaves the app.

Match confidence

MatchConfidenceRule
ExactResolvedSame method and the same path segments, with parameters lining up
Shared prefixInferredThe route's path is the tail of the call's path, because the backend mounts its routers under a prefix it reads at runtime (for example /api/v1 from a setting). Literal segments outrank parameters, so /users/me beats /users/{id}.
TiePossibleTwo or more routes match equally well. Lantern links each one as possible and never picks silently.
Why this matters for security

Once the frontend and backend share one graph, reachability (Section 9.2) runs across the network boundary. A finding deep in the backend can be traced to the exact page and button that reach it, and a route the frontend calls with no login check on its path stands out on the map.

6.5Entry-point detection and scale

Large repositories produce graphs too dense to read. Lantern never opens on the whole graph. It detects entry points and starts there:

  • Detected automatically: if __name__ == "__main__", fn main, int main, console-script and binary targets in pyproject.toml, package.json, Cargo.toml, and CMake; route decorators for Flask, FastAPI, Django, Axum, and Actix; Next.js pages and route handlers, React Router and TanStack Router file routes, and Express-style app.get("/path", handler) servers; app starts such as createRoot and .listen(); CLI frameworks such as Click, Typer, argparse, and clap; and test functions.
  • Pages and buttons: frontend entry points are pages, and event handlers wired in JSX (onClick, onSubmit) appear as the first hops beneath them, so a user can start from "what happens when someone clicks Save?"
  • Collapsing: modules collapse into single nodes until expanded. Calls into the standard library and third-party packages collapse into an "External" boundary node by default.
  • Incremental runs: each callable is fingerprinted by a hash of its normalized syntax tree. Re-runs only re-resolve changed files and only re-explain changed callables, which keeps repeat runs fast and cheap.

07 · ExplanationsThe Three-Lens explanation system

Each node can be read three ways. The third lens is the product's signature: it teaches the vocabulary instead of hiding it.

7.1The three lenses

LensAudience and rules
1 · TechnicalFor engineers. Precise terminology, inputs and outputs, side effects, error behavior, complexity where relevant, and the role the function plays in its call path.
2 · EverydayFor anyone. No jargon. Must include at least one concrete example ("if a user types…") and one analogy. Analogies come from a single metaphor world chosen per repository, so explanations stay consistent across the whole map.
3 · MappedA bridge. The everyday explanation, rewritten so that every plain phrase is paired 1:1 with the exact technical term, symbol, or line it stands for. Tapping either side highlights its twin.

7.2Worked example

Function: auth.verify_token(token: str) -> User in a FastAPI app. Metaphor world for this repository: a hotel.

Lens 1 · TechnicalDecodes a JWT with HS256 using the JWT_SECRET environment variable, validates exp and iss claims, then loads the user by the sub claim through UserRepo.get(). Raises HTTPException(401) on any decode or lookup failure. Called by the get_current_user dependency on every protected route.
Lens 2 · EverydayThis is the front desk checking a room key. When someone tries to enter a members-only part of the app, they show a key card. The desk checks that the card was made by this hotel, hasn't expired, and belongs to a real guest. If anything is off, the guest is turned away. For example, a card issued yesterday that was only good for one hour gets rejected.

7.3Keeping the mapping honest

A plain-English layer is only valuable if it's anchored to reality. Lantern enforces that mechanically:

  • Structured output. Models return a JSON object, not free text (schema below). Each Lens 3 pair carries an anchor: a symbol ID from the graph, a source line range, or a vocabulary term from a curated glossary.
  • Anchor validation. Every anchor is checked against the graph and the source. Pairs with anchors that don't exist are rejected, and the explanation is regenerated or flagged. A model cannot invent a function that isn't there.
  • Grounding context. The prompt includes the callable's source, its callers and callees from the graph, any security findings on it, and the repository's metadata. Models explain what the graph shows, not what they guess.
  • Glossary build-up. Technical terms that recur across a repository (JWT, middleware, mutex) gain a glossary entry in all three lenses, so a learner can browse vocabulary on its own.
// Explanation record (abridged)
{
  "node_id": "py:auth.verify_token",
  "code_hash": "b3f1…9a",  "model": "provider/model-name",  "prompt_version": "lens-v3",
  "lens1": { "summary": "…", "inputs": [ … ], "side_effects": [ … ], "errors": [ … ] },
  "lens2": { "text": "…", "example": "…", "analogy": "…", "metaphor_world": "hotel" },
  "lens3": [ { "plain": "the front desk", "technical": "verify_token()",
               "anchor": { "type": "symbol", "id": "py:auth.verify_token" } }, … ],
  "validated": true
}

7.4Generation strategy

  • Bottom-up, then top-down. Leaf functions are explained first, so callers can reference what their callees do. Module and entry-point summaries are generated last from their members' explanations.
  • Lazy by default. Entry points and their first three levels of calls are explained eagerly. Everything else is explained when first opened, which keeps the first run's cost low. "Explain everything" is one tap, with a cost estimate first.
  • Path narratives. In Flow view, the user can ask for a step-by-step story of one entry point's path ("what happens when someone logs in"), in any lens.

08 · ModelsModel choice: the multi-LLM layer

Users choose the model for each job, see what it will cost before it runs, and can always tell which model wrote what.

8.1Provider support

  • Bring your own key (BYOK) for major providers: Anthropic, OpenAI, Google, Mistral, and aggregators such as OpenRouter that expose many models behind one key.
  • Local and self-hosted models through any OpenAI-compatible endpoint, which covers Ollama, llama.cpp's server, vLLM, and LM Studio.
  • Adapter design. A thin internal interface with three adapters (OpenAI-compatible, Anthropic, Google) covers nearly every provider. The cloud backend MAY use a gateway library such as LiteLLM for routing, spend tracking, and fallbacks; the agent ships its own small adapters so it stays a single dependency-free binary.
  • Capability checks. Before a model is selectable for a task, Lantern runs a short probe for structured JSON output and context length. Models that fail the Lens 3 schema reliably are marked "not recommended for Mapped lens."

8.2Per-task routing

TaskWhat it needsTypical choice
Lens 1–3 explanationsHigh volume, structured output, good writingA fast, inexpensive model
Path narratives and module summariesLong context, synthesisA mid-tier model
Security triage and fix draftingCareful reasoning, low error toleranceThe strongest model available
Systems-design advisorBroad knowledge, judgmentThe strongest model available

Users can accept a recommended routing preset (Economy, Balanced, Best) or set each task by hand.

8.3Cost, caching, and transparency

  • Cost preview. Before any model run, Lantern estimates tokens from the graph's size and shows a price range per provider. Users can set a hard spend cap per run and per month.
  • Cache key. (code_hash, context_hash, model, prompt_version, lens). An unchanged function is never paid for twice. Changing models doesn't discard the cache; both versions are kept.
  • Attribution. Every explanation, triage note, and fix shows the model that produced it and the date. Reports list all models used.
  • Compare mode. Any node can be explained by two models side by side. This doubles as a quality check and helps users pick a default.

8.4Key custody

ModeWhere keys live
Local agentThe OS keychain (macOS Keychain, Windows Credential Manager, Secret Service on Linux). Never transmitted to Lantern.
CloudEnvelope-encrypted: a per-user data key encrypts the API key; a managed KMS key encrypts the data key. Decrypted only inside the worker for the job's duration. Never logged, never returned to any client after entry; the UI shows only the last four characters.

Licensing: requires legal review before launch

In December 2024 Semgrep moved its maintained rules to the Semgrep Rules License v1.0, which limits them to internal, non-competing, non-SaaS use. The engine itself remains LGPL 2.1. Lantern's cloud mode is a SaaS, so it MUST NOT bundle Semgrep-maintained rules there. The plan: run the Opengrep fork (or the LGPL engine) with Lantern's own rules plus permissively licensed community rules. In local mode, the agent MAY run a user's own Semgrep installation and rules, since that is the user's internal use; counsel should confirm this reading.

9.2The finding lifecycle

  1. Collect and normalize. All scanner output is converted to SARIF, deduplicated, and attached to graph nodes by file and line.
  2. Reachability. Lantern checks whether the affected function is reachable from any entry point, and whether untrusted input (a route parameter, file upload, CLI argument) can flow there along graph edges. Reachable findings rank up; unreachable ones rank down but are never hidden. This is the feature engineers will value most: it separates real risk from noise.
  3. Triage. The chosen model explains the finding in all three lenses and gives a likelihood that it's a false positive, with reasoning. Models MAY flag a likely false positive; they MUST NOT dismiss one. Only the user can mark a finding as accepted risk, with a written reason that appears in the report.
  4. Fix. The model drafts a minimal patch as a unified diff, with a Lens 2 explanation of what changed and why.
  5. Verify. After the patch is applied, the same scanner re-runs on the affected files. A finding is only marked "fixed" when the scanner agrees.

9.3Severity model

RankRule
CriticalHigh scanner severity, reachable from an entry point, and touched by untrusted input. Also any live secret.
HighHigh severity and reachable, or a known-exploited dependency vulnerability.
MediumMedium severity and reachable, or high severity but unreachable.
LowEverything else, including hardening suggestions.

9.4Security features to add

Beyond finding bugs, Lantern recommends protections the app is missing, based on what the graph shows it does. Each recommendation names the evidence that triggered it.

If the graph shows…Lantern suggests

Route input reaching a database callParameterized queries or an ORM, input validation schemas (Pydantic, serde with validation)

10.2Systems-design advisor

The advisor classifies the project's shape from the graph (web API, background worker, CLI tool, library, desktop app, data pipeline), then recommends a deployment pattern and explains it in all three lenses.

  • Shape-specific advice. A web API gets twelve-factor configuration, a container, a managed database, a reverse proxy, and horizontal scaling notes. Long-running request handlers get a recommendation to move work onto a queue. A CLI gets release packaging and cross-platform builds.
  • Hotspot detection. The graph reveals fan-in hotspots (one function everything depends on), synchronous network calls inside loops, and database calls inside request loops (the N+1 pattern). Each is flagged with the path that shows it.
  • Generated starter files. Dockerfile, .dockerignore, a GitHub Actions workflow that runs tests and Lantern's scanners, .env.example, SECURITY.md, and a health-check handler. Each is delivered as a diff the user reviews; nothing is committed silently.
  • Architecture diagram. A one-page diagram of the recommended deployment, which can be included in the Evidence Report.

11 · EvidenceThe Evidence Report

The deliverable that changes the conversation with a skeptical engineer: short, verifiable, and honest about its limits.

11.1Contents

  1. Header. Repository, commit hash, branch, analysis date, mode (cloud or local), and privacy level.
  2. Scorecard. Readiness score with category breakdown; finding counts by severity, before and after fixes.
  3. Architecture. Entry points, the top-level Atlas, and the recommended deployment diagram.
  4. Security. Open findings, fixed findings with verification status, and accepted risks with the builder's written reasons.
  5. Understanding. The builder can attach path narratives they've reviewed, demonstrating they know how key flows work.
  6. Provenance. Every tool and version used, every model used, and the rule sets applied.
  7. Limits. A required, plain-language section stating what the report does not prove, such as runtime behavior not covered by tests, business-logic flaws scanners can't see, and lower accuracy for dynamic code or C++ analyzed without a compile database.

11.2Verifiability

  • Each report gets a public, unguessable link and a PDF export. The builder can revoke the link at any time.
  • The report includes a signed digest of its results and the commit hash. A reviewer can re-run the same analysis on that commit with the open-source agent and compare.
  • A README badge can show the latest score, linked to the full report.
Why open-source the agent

An engineer who doubts the report can read the code that produced it and run it themselves. That is the strongest possible answer to "this is just AI output." The commercial value sits in the hosted experience, the explanations, the PWA, and team features, not in the scanner orchestration.

17 · Risks and metricsRisks, open questions, and success metrics

The biggest risks are trust risks. Most of the design above exists to reduce them.

17.1Risks

RiskImpactMitigation

17.2Open questions

  1. Final product name, plus trademark and domain availability.
  2. Backend language: Python or TypeScript. Decide by team skills in Phase 0.
  3. Should metaphor worlds be chosen by the user, by the model per repository, or from a curated set?
  4. Open-source license for the agent: permissive (Apache 2.0) or copyleft (AGPL)?
  5. Should the Evidence Report support a reviewer sign-off, letting an engineer attest they reviewed it?
  6. Which second code host to add after GitHub, if any, for cloud mode?
  7. Which hosted backends to model first as database edges with access-rule checks: Supabase, Firebase, or both?
  8. Should Lantern read a backend's OpenAPI document, when one exists, to turn prefix matches into exact ones?
