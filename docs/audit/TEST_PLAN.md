# Test plan

## 1. Automated checks (run these first)

```bash
bash tools/audit.sh              # everything below except the browser step; about 1 minute
bash tools/audit.sh --browser    # adds the Chromium viewer and app checks
```

| Step in `tools/audit.sh` | Command | Pass when |
|---|---|---|
| Unit and integration tests | `python -m pytest -q` | all pass (88 at the time of writing) |
| Self-audit | `lantern analyze . --out $W/self --fail-on medium` | exit 0 |
| Sample: React + FastAPI | `lantern analyze tests/fixtures/shop` | 3 critical, 1 high; shell injection path from `/admin`; the SQL injection followed from the request |
| Sample: Next.js + Supabase | `lantern analyze tests/fixtures/nextapp` | finds `LW-AUTH-MISSING`, `LW-NO-RLS`, public service-role var |
| Determinism | `lantern verify` on a temp git repo against its own report | MATCH, then DIFFERENT after a code change |
| CLI surface | `lantern --help`, `starter`, `accept`, `evidence` | exit codes as documented |
| Offline model end to end | `tools/fake_model.py` + `lantern explain --model openai-compatible/demo` | explanations validated for the demo units |
| Browser (optional) | `node tools/viewer_smoke.js` | "no JS errors" at desktop and phone sizes; also on a report whose every field carries an HTML payload (`tools/poison_report.py`): nothing lands as markup, the title never changes; and on one where only the scenarios carry it (`--only scenario,dropped_scenarios`), so the finding cards, Fix page and Scenario lens that show them are drawn and checked |
| Live app (with `--browser`) | `node tools/viewer_smoke.js --app URL OUT --image shot.png --expect-text 7351` against `lantern serve tests/fixtures/shop` | "no JS errors" and each step answers: "Watch my tests run" is confirmed and runs in the sandbox (toast says tests ran), the Terminal drawer runs `analyze --offline` (prints `ready`) and refuses `rm -rf /`, a generated screenshot dropped into Ask Lantern is read on this computer (the text when Tesseract is installed; CI installs it), Settings → Analysis packs turns Django off (the project card goes "Re-check to apply") and back on |

CI runs the tests and the self-audit on Python 3.11, 3.12, and 3.13 for every push (`.github/workflows/ci.yml`).
The tests never reach the internet or a real model provider, and never see the keys of whoever runs them
(`tests/conftest.py`, `tools/netguard/`): the run gets an empty temporary home, every key and sign-in variable is taken
out, real providers are switched off, and a test that tries the network fails even when the code hid the error. On
Linux, CI runs them through `tools/netless.py --watch`, in a network that holds only the computer's own address, with
the operating system writing down every address any program tries; the count is in the job summary and anything but 0
fails the step (a try a test names before it makes it, for an address kept for examples, that the kernel refused, is
written apart with its reason: the sandbox's JavaScript twin, the one program below Python that tries the outside to
see the refusal). `tools/audit.sh` and the self-audit steps run through `tools/netguard/lantern_netguard.py --allow
pypi.org,registry.npmjs.org,api.osv.dev` (the dependency audit's addresses, nothing else). To see it refuse: `python
tools/netguard/lantern_netguard.py -- python -c "import urllib.request as u; u.urlopen('https://example.org')"`
prints the refusal, lists the attempt and ends with a non-zero result. The live suite (`bench/explain_eval.py`,
`bench/ask_eval.py`, the `model-eval` workflow) is the only place a real provider is used, and only with `--live
--model … --destination … --max-requests …`; run either script without them to see it refuse.
The `install` job does what a tester does on Linux, macOS and Windows: a clean venv, `pip install
"git+https://github.com/LittleHenderson/Lantern@<commit>"` with no extras, then `lantern --version` (0.11.0),
`lantern analyze tests/fixtures/shop --offline` (prints an `off` line naming the scanners that are not installed)
and `lantern serve tests/fixtures/shop --check` (starts, prints the link, loads the app once, exits 0).
The `gateway` job curls the live gateway's `/v1/health` (`https://lantern-gateway.fly.dev`) on every push and prints
it to the job summary; it fails when the gateway does not answer `ok` with a model configured. The limits it enforces
are listed in `docs/deploy.md` ("Free allowance limits as configured").
Retention (90 days for token hashes and per-day counters, `Store.prune`) is tested in `tests/test_gateway.py`:
idle and rotated-out hashes and their account mapping go, a hash in use and rows exactly 90 days old stay, an old
database gains the `last_used` column, and the app prunes at start-up and on the first request of a new day.
Speed (directive point 10) is measured by hand, not in `tools/audit.sh`: `python bench/speed.py WORK [--only shop]
[--browser]` analyzes the sample shop and five public apps at a fixed commit each (the clones stay in `WORK`, so a
later run reads the same code), three first runs and three repeat runs of each, then one repeat run with kept work
switched off and one first run on kept work, and says for each project whether every result file is the same in all
of them (`same: yes`); a difference is named and the result is 1. To compare two engines, measure the older checkout
first (`--engine OTHER --json before.json`) and then this one with `--compare before.json --must-match`: the result
is 1 when a result file both engines write, or what the two reports hold, differs. It reaches github.com for the
clones and nothing else (`netguard.begin`). The numbers of the last run are in `bench/speed_results.md`.
A pushed `v*` tag runs `.github/workflows/release.yml`: build sdist + wheel, the test suite against the built wheel
with the source folder moved away, the live gateway's `/v1/health`, then a GitHub Release with both files. Started
by hand (`workflow_dispatch`) the same workflow is a rehearsal: everything but the publishing job, which runs only
for a pushed tag. A test that reads Lantern's own pages or modules takes them from the package Python loaded
(`tests/lantern_files.py`), so it holds against the built wheel too; on 2026-11-12 twelve tests that read them
through the checkout failed in a trial of the 0.11.0 release build (4,276 passed, 27 skipped, 12 failed on 84d5c1e).

## 4. Adversarial cases to try

4.1 **XSS through the analyzed repo.** Create files and functions named `<img src=x onerror=alert(1)>` (valid as a
string in routes and JSX text, a filename on Linux), a route path containing `"><script>`, and a docstring with
`</script>`. Analyze, open `report.html` and `evidence.html`, and check nothing executes.

4.2 **XSS through model output.** Make `tools/fake_model.py` return `<script>` in `lens1.summary`, a string instead
of a list in `lens1.inputs`, and `{"type":"lines","start":"<b>1</b>"}` as an anchor. Explain and view.

Last run 2026-10-31 after the UI redesign (Chromium, both report.html and evidence.html, every lens opened, light and dark):
no script executed for 4.1 or 4.2; `tools/audit.sh --browser` all pass. Re-run after any viewer change.

4.3 **Local server from another origin.** From a page on `http://localhost:9999`, `fetch('http://127.0.0.1:8765/api/
state', {credentials:'include'})` and a form POST to `/api/projects/<id>/analyze`. Both must fail. Repeat with a
rebinding-style Host header: `curl -H 'Host: attacker.test:8765' …` must get 403.

4.4 **Path tricks.** Starter `name` values `../x`, `/etc/x`, `a/../../x`; a project path given as `~/../..`; a symlinked
directory inside the repo pointing at `$HOME`.

4.5 **Accepted-risk abuse.** Hand-write `lantern-accepted.json` with an empty reason, an unknown id, a non-list, and
invalid JSON. Lantern must ignore bad rows and keep working.

4.6 **Resource exhaustion.** A 50 MB minified JS file, a 10,000-level nested expression, a line of 1 MB of `(`, a
repo with 100,000 empty files, deeply nested directories. Note time and memory for `lantern analyze`.

4.7 **Honesty checks.** Pick five edges labeled "confirmed" and five "likely" in a real repo you know, and check each

4.8 **Determinism.** Run `lantern analyze` twice on the same commit and diff `evidence.json` `payload`. Only
`generated_at` and timings should differ, and they are outside the digest.

4.9 **Key leakage.** Set a fake key, trigger a provider error (wrong base URL, a server returning 401 with the request
echoed), and search `~/.lantern`, `.lantern/`, job logs (`/api/jobs/<id>`), and the terminal for the key.
