# Threat model

Scope: Lantern as built today, running locally (`lantern serve` or the CLI), plus the cloud service (`cloud/`,
milestones 1–6: sign-in, runs from a link, results in the browser, the website, sharing and deleting, explanations
and Ask Lantern through the allowance), see T7.

## Assets

| Asset | Where it lives |
|---|---|
| The user's source code | Their repo; copies of function bodies in `report.html` (privacy `full`) and in prompts sent to a cloud model |
| Model API keys | Environment variables; server memory; `~/.lantern/keys.json` (0600) if "remember" is ticked |
| Other files on the user's machine | Anything the user account can read |
| Integrity of results | `security.json`, `readiness.json`, `evidence.json`, the digest; what a reviewer relies on |
| The user's attention and trust | UI wording about where code goes, how sure an edge is, what a score means |

## Trust boundaries

1. **Analyzed repository → Lantern.** Repos are untrusted input: a user may analyze code they cloned from anywhere.
2. **Model output → Lantern.** Text from any provider (or a hostile endpoint) is untrusted.
3. **Browser (other websites) → local server.** Any page the user visits can send requests to `127.0.0.1`.
4. **Lantern → model provider.** Code leaves the machine here, only on request, only to the configured endpoint.
5. **Shared reports → their readers.** `report.html` / `evidence.html` are opened by other people.

### T2. Other websites attacking the local server

| Attack | Mitigation | Where |
|---|---|---|
| Cross-site request forgery against write endpoints | Writes need the `X-Lantern-Token` header (a custom header forces a CORS preflight, which the server never approves) | `Handler._write`, `_authed(True)` |
| Cross-site reads (JSON of projects, reports) | Reads need the `lantern_token` cookie (SameSite=Strict, so not sent on cross-site requests); browsers' same-origin policy blocks reading responses | `_authed(False)` |
| DNS rebinding (attacker domain resolves to 127.0.0.1) | Host header must be `127.0.0.1:PORT`, `localhost:PORT`, or `[::1]:PORT` | `_host_ok` |
| Another local user on a shared machine | Needs the token printed in the starting user's terminal; 127.0.0.1 only | `serve` |
| Clickjacking the app | `X-Frame-Options: SAMEORIGIN` | `_send` |
| `--host 0.0.0.0` exposes it to the network | Prints a warning; token still required; plain HTTP | `serve` | **Use only on trusted networks** |
| Token leakage through the address bar or Referer | Token link redirects to `/` after setting the cookie; `Referrer-Policy: no-referrer` | `do_GET` |

Note: the token is also embedded in `app.html` and in served reports (`window.LANTERN_LIVE`), so anything that can run
script in the app's origin can act as the user. That makes XSS in the viewers (T1, T3) the main path to a takeover.

### T4. Key handling

* Keys pasted in Settings are held in memory by default; "remember" writes `~/.lantern/keys.json` with `O_CREAT` mode
  0600 via a temp file and atomic replace (`Store._write`).
* `/api/state` and `/api/settings` return only where a key came from, never the key (`test_keys_stay_private`).
* Keys are never written into `.lantern/`, reports, or the Evidence Report. Check job logs and tracebacks: provider
  errors include the HTTP body from the provider, which could echo request details (**review**).
* On Windows, mode 0600 has no effect; the file relies on the user profile's ACLs (**open**, documented here).

* Tests and benchmarks never use a key: every run takes the key, token and sign-in variables out of its environment
  and moves the home folder (where `lantern login` and `keys.json` live) to an empty temporary one before anything
  else happens (`tools/netguard/lantern_netguard.py` `scrub`, `temp_home`; `tests/test_isolation.py` plants 19 keys
  and a saved sign-in and shows no test can read them). The only place a real provider is used on purpose is the
  live suite (`bench/live.py`), which needs the model, the one destination and a request cap on the command line and
  never falls back to a key it finds.

### T5. Code leaving the machine

* Only `explain` sends code, only to the configured provider, and the UI says so in plain words when the provider is
  not local (spec 5.3). `openai-compatible` counts as local only when its base URL is localhost/127.0.0.1.
* `analyze`, `verify`, scanners, and the server make no network calls except the dependency audits: pip-audit
  (PyPI/OSV) and `npm audit` (registry.npmjs.org). They send package names and versions, never code (since
  2026-11-12 also the name and the version that a copy of a package under a `vendor` folder gives in its own
  `package.json`, to OSV: `unread.NPM_NAME`, `NPM_VERSION`; never for a `private` package). `--offline` or
  `LANTERN_OFFLINE=1` turns them off. The three hosts they ask are `depaudit.AUDIT_HOSTS` (pypi.org,
  registry.npmjs.org, api.osv.dev); CI's self-audit runs with every other address refused and passes.
* Since 2026-11-13 a test run in the sandbox ("Watch my tests run", `lantern analyze --trace --sandbox`) fetches the
  libraries the project names before the tests start (`lantern/libraries.py`). pip and npm are started by the
  sandbox's launcher and reach nothing but Lantern's doorkeeper on this computer (`lantern/_stores.py`), which lets
  through the store's own hosts and refuses and writes down every other address: pypi.org and
  files.pythonhosted.org, registry.npmjs.org, or the stores the person named in `LANTERN_STORE_PYTHON` /
  `LANTERN_STORE_NPM`. What leaves is what a `pip install` or `npm ci` of those names sends: library names and
  versions, never the project's code. The project's tests then run with the network off. `--offline` or
  `LANTERN_OFFLINE=1` fetches nothing (the tests run on what is installed when every library the project names is
  there, and are otherwise not run, with the missing ones named). `analyze` without a test run, `verify`, the scanners and the server fetch nothing.
  `LANTERN_NO_REAL_PROVIDERS=1` refuses every model and gateway address that is not on this computer
  (`providers.check_destination`); every test and benchmark run sets it. Only `name==version` pairs reach pip-audit (index options in the repo are
  ignored), and `npm audit` gets `--registry` explicitly and is started in a folder of Lantern's own, so a repo's `.npmrc` is not read at all (until 2026-11-10 it could not redirect the audit but could switch it off or name a proxy: CLAIMS A4h). Earlier note: `pip-audit` queries a
  vulnerability database when `requirements*.txt` exists (**document in UI**: currently only in Provenance).
* Opt-in usage counts (`lantern/usage.py`; off until the person turns them on) go to one address, the gateway's
  `/v1/usage` (`usage.destination`): `https`, or `http` on this computer only, no name or password in the address, no
  redirect followed, nothing for another computer while `LANTERN_NO_REAL_PROVIDERS` is set, and never more than the
  install id, the version, the operating system's name and a count per feature. `lantern usage --show` says where
  they go, or why they do not. Until 2026-11-10 they were posted to an address the gateway does not have (none
  arrived), a redirect was followed and its answer taken for the gateway's, and the switch was not asked. Tests:
  `tests/test_usage_address.py`. What the gateway does with what it is sent: T8.

### T7. Cloud service (`cloud/lantern_cloud/`)

Strangers paste links to repositories Lantern has never seen, on a server Lantern's owner pays for.

| Attack | Mitigation | Where | Status |
|---|---|---|---|
| A hostile repository runs code on the server, reaches the network during analysis, or keeps files | Clone into a temp folder (size cap before checkout); dependency audits in the restricted process with network; analysis (`lantern analyze --offline`) in the restricted process with **no network** and writes only in its temp folder (the same `_jail` as the test sandbox); the temp folder, clone included, removed in `finally`; `blocked` when the sandbox stopped something. Each step's launcher ends everything the step started when the step ends, at its time limit, when the service shuts down (`Worker.shutdown`, called from the app's lifespan; the run is recorded as failed with "Lantern was shut down while this run was going") and when the service's process is killed (`parent` in the launcher's policy). ### T8. The gateway: callers who have not signed in (`gateway/lantern_gateway/`)

The gateway holds the owner's model keys and answers some addresses for anybody: the health check, the sign-in
pages, the owner's page (it asks for the secret) and the app's opt-in usage reports. Gateway 0.2.6
(`limits.py`); measured against the gateway's own code with stand-ins for the model and GitHub, never against the
live gateway.

| Attack | Mitigation | Where | Status |
|---|---|---|---|
| A very large body from nobody is read whole | No body is read past the limit of its address (`LANTERN_MAX_BODY` for the model route, 4,000 bytes elsewhere): a declared size over it is refused before reading, an undeclared one at the piece that crosses it (413) | `limits.BodyCap` | Mitigated, tested in the app and on a real connection (before: 32 MB taken whole on three addresses) |
| A body of another shape makes the gateway fail | A body that is not a JSON object, or nested deeper than Python follows, is answered 400 in the gateway's words; a `max_tokens` that is no number is the cap | `_table`, `_size` | Mitigated, tested (before: HTTP 500 for 12 shapes) |
| Invented installs or free text fill the owner's numbers | Reports per sender per hour, new installs per sender per day and for everyone per UTC day; a version only in the shape of one, an operating system only from three names | `usage`, `Store.record_usage`, `USAGE_VERSION`, `USAGE_SYSTEMS` | Bounded, tested. A caller with many addresses can still add installs up to the day's cap for everyone (1,000 by default) |
| The owner's secret is guessed | Five wrong secrets a minute per sender, 30 for everyone together, then no secret is looked at until the minute ends; compared as bytes in constant time | `admin` | Slowed, tested. The cost: callers from many addresses can keep the owner waiting for their page |
| A copy of the database holds a working token | The token that waits for the app is sealed with the app's own code; the gateway keeps a hash of the code; a row in clear from an earlier version is deleted at start-up, never handed out; everything else is hashes | `_seal`, `_open`, `Store.park`, `Store.claim` | Mitigated, tested. Someone who has the server's log lines of those ten minutes (they hold the code) and the file can open it |
| A sign-in link is used again and again so that the gateway asks GitHub or Google each time | A link works once; the provider is asked at most 10 times a minute for one sender and 120 for everyone together | `first_use`, `auth_callback` | Mitigated, tested (before: 200 uses, 200 requests to GitHub) |
| The provider is down or answers with something else | The person gets a page (502), not an internal error | `auth.exchange` | Mitigated, tested |
| The limits themselves keep a record of who called | A sender is kept as a keyed hash, in memory only, with a key that exists only while the process runs; at most 20,000 per kind | `limits.Limiter` | Tested (`test_no_address_is_kept`, `test_the_table_of_senders_cannot_grow_without_end`) |

## Known open risks, ranked

0. A restricted step of the cloud service may read what the service's own user may read (T7): its walls stop writes and the network, not reads. Nothing known runs a stranger's code inside a step since 2026-11-10 (`lantern/gitfacts.py`), but the next such hole would again reach other people's stored results. A step under a user of its own, or results it cannot see, would close that. Measured 2026-11-10 with a stand-in value, service and step as one ordinary user: with Landlock on (ABI 7) the step is refused the service's own environment (`/proc/<pid>/environ`; Landlock keeps a process from looking into one outside its walls), and a program of that user with no Landlock reads it. So on a kernel without Landlock such a hole would also reach the service's secrets. Every step says which it had in the run's log (`sandbox: Landlock on (ABI n…)`, or `sandbox: Landlock kernel has no Landlock`).
1. Regex/CPU exhaustion on adversarial repos is untested (T1).
2. A committed `lantern-accepted.json` can silence `--fail-on` (T1); needs a review rule.
3. Readiness can be satisfied by placeholder files (T1); disclosed in Limits.
4. Provider error text may surface in job logs; check it never includes the key (T4).
5. `--host` beyond localhost serves plain HTTP (T2).
6. No signature on the Evidence Report, only a digest (stated in the report).
7. The gateway's limits on callers who have not signed in count senders by address (T8): a caller with many
   addresses can use up the counts for everyone for a minute at a time (the owner's page, signing in), and whether
   a caller can name its own address through Fly's proxy was not tried.
