# CLAUDE.md

Context for working on Lantern in Claude Code. The product spec is `docs/Lantern_Product_Spec_v0.4.pdf`.
This repo is Phase 0 plus the full-stack layer: Python, TypeScript/JavaScript, Go, Rust, Java, Kotlin, Swift, Dart, C#, PHP, Ruby and C/C++ engines, the API bridge
between them, scanners, the Three-Lens explainer, and a static HTML report.

**Audience:** AI-assisted ("vibe") coders whose apps are usually full stack, often TypeScript. The
product's job is to make their code understandable and defensible to skeptical engineers.

## Non-negotiable principles (from the spec)

1. **Facts from tools, words from models.** Call edges, HTTP links, findings, and reachability come
   from deterministic code. Models only explain, and never create, dismiss, or close a finding.
2. **Show confidence, never fake certainty.** Every edge has `observed | resolved | inferred | possible`
   plus a `via` saying how it was resolved. A new rule gets a confidence level backed by `bench/`
   numbers: "inferred" (UI: "likely") needs about 90%+ measured precision across repos.
   Unresolvable calls are counted in `graph.unresolved`, not guessed.
3. **Every Lens 3 pair must anchor** to an allowed symbol, a line range inside the unit, or a term found
   in the source or `GLOSSARY`. `explain.validate()` enforces this; don't loosen it to make a model pass.
4. **Lantern must pass its own audit.** `lantern analyze .` should report no critical/high/medium. CI
   enforces it. (It caught two false positives in the web rules during development.)
5. **Heuristic checks say so.** Graph/pattern-based security rules that can misfire set
   `tool_confidence: LOW`; the viewer labels them "heuristic". Protections have three statuses: `add`, `check`
   (an app-wide mechanism exists but the code does not show it covers the routes in question), `in place`.
6. **Everything in the viewer is escaped.** Every value from the data goes through `esc()` (class names through
   `cls()`), and `render()` adds a hash-based Content-Security-Policy so a report opened from disk cannot run
   script planted in its data. CI opens a poisoned report (`tools/poison_report.py`) in Chromium to prove it.

```bash

node tools/report_perf.js /tmp/shop/report.html       # does the report open and respond on a slowed phone (8 s / 2 s budgets)
python tools/load_test.py http://127.0.0.1:8872 /tmp/tok   # 50 readers on the cloud website demo, no errors, p95 under 1.5 s
node tools/viewer_smoke.js /tmp/demo/report.html /tmp/shot   # screenshots, JS errors, accessibility (axe-core + a keyboard
```

## How Python resolution works

The walker emits `CallSite`s with a `kind`: `call`, `depends` (FastAPI `Depends(fn)`), `depends-alias`
(`Annotated` alias defined elsewhere), `decorator-result` (closure a decorator factory returns), `attr`
(kept only if it hits a `@property`), `with` / `with-obj`. Typing sources: `self`/`cls`; `self.x = Foo()`;
`x = Foo()` / `x = make()` (return type) / param hints / `with Foo() as x`; pytest fixtures by name.
Built-in literal locals (`literal_types`: every binding of the name in that scope is a literal or built-in constructor of one type, not a parameter; loops, `except as`, `nonlocal`/`global`, `match` captures and lambdas spoil it; `x = list()` counts only while nothing rebinds `list`: a repo def, import, parameter or assignment, `Resolver._shadowed`) make `x.append()` a built-in call (`via: literal-type`). Built-in calls are counted in `g.builtin_calls` (`call_sites()['builtin']`), never drawn.
Imports go through a suffix index (`from app import crud` → `backend.app.crud`); stdlib names never remap.
Star imports (stage 3): `from x import *` of a repo file brings what Python would bring (`Resolver._star`): the names in `__all__` when it is written once as a list of strings, else every name without a leading underscore; the last star import wins; a package `__init__` that says `from .users import *` re-exports them (`from app.auth import find_user`). Not followed when the name is a parameter, a local or a variable of the file, when a later star import is one Lantern cannot read (a library's, a file that is not there), or when `__all__` is built another way: the call stays unresolved (`not-defined`, `repo-variable`).
Library base classes (stage 3): a method or attribute a repo class does not define, on a class whose first base outside the repo (along the MRO; `abc`, `typing`, `enum`, `dataclasses`, `object` skipped) is a library class, is a library call `ext:<pkg>.<Base>.<member>` (`via: inherited-library`, `inherited-builtin` for a built-in base; `likely`), unless the repo itself sets that attribute (`Resolver._repo_attr`): `self.assertEqual`, `Note.objects.filter`. No library claim is made when the class also has a base Lantern cannot identify (`Resolver._outside`: a library's star import, a computed base, a subscripted repo class `Repo[Note]`, or a class from a project file it did not read); the call stays unresolved with reason `unknown-base`. A relative import that finds no file names a project file, never a library (`ImportBinding.relative`, `Resolver.gone`): the graph keeps the older `ext:` edge, the inventory says `missing-module` (`Resolver.unread`), and the stage-3 rules do not build on it. A call on what a library call returned is a library call (`ext:pandas.read_csv().head`, `via: library-result`); built-ins stay built-ins. A library label is never given where the function may be the project's own (the older reading stands instead: a name-only guess, or unresolved with reason `library-or-repo`): `self.<attr>.<m>()` through a library base's attribute only one step deep and only when no repo class has a method `<m>`; `<lib call>().<m>()` only when no repo class has a method `<m>` (`Resolver.library_result(guard=)`; everyday names in `GENERIC_METHODS` do not count, `str(x).title()` stays a built-in); `self.<m>()` not when a sibling mixin gives a subclass that method (`Resolver._sibling_gives`). Router prefixes: `app.include_router(r, prefix="/api")` and Flask `register_blueprint(bp, url_prefix=…)` give the router's routes their full path (`Resolver.mount_prefixes`; Flask's `url_prefix` at registration replaces the blueprint's own).

## How JS/TS resolution works

`Walker` records defs (functions, arrow functions assigned to names, `memo`/`forwardRef` wrappers,
classes and methods, inline route handlers), imports/exports (default, named, namespace, `export *`,
`export { a as b } from`), and refs with kinds `call`, `new`, `jsx` (rendering `<Comp/>`), `callback`
(function passed by name; `ui` set to `onClick` etc. when inside an event prop). Anonymous inline
functions are attributed to the enclosing named function. HTTP calls: `fetch`/`$fetch`/`useSWR`,
`x.get|post|...(url)`, `x.get({url})` (generated clients), `axios({url, method})`; URLs from strings,
template literals (`${id}` → `{}`), `+` concatenation, and module-level string constants.

Script inside HTML pages (`.html`/`.htm`, `js_frontend.inline_script`): the JavaScript `<script>` bodies are laid over a
buffer of spaces at their original offsets (line numbers are the page's own) and parsed with the JS grammar; the module
keeps the `.html` in its name (`js:site/index.html::load`), the file node is a `page` entry (Browser lane; its functions
Frontend). JSON/importmap/`text/babel` blocks, `src=` tags and `.min.html` are skipped. Built bundles
(`js_frontend.built_bundle`: over 50 KB with lines averaging 500+ characters or one over 50,000) are not read, whatever
their name; `report.collect_sources` cuts lines at 2,000 characters, 40,000 per function, 40 M in all. `LJ-*` pattern rules do not run on
pages (a page that builds itself with `innerHTML` from escaped values would light up on every line).

Entries: Next.js (`app/**/page`, `app/**/route` exports, `pages/**`, `pages/api/**`, only when the
nearest `package.json` depends on `next`), `createFileRoute`, React Router `<Route>` and route objects,
`createRoot().render` (SPA start), Express-style `app.get('/x', handler)`, test files.

CommonJS and Express (stage 3): `require('<literal>')` binds like an import (`require:<spec>` heads); `module.exports = …`, `exports.x = …`, `module.exports = new X()`, constructor functions (`this.x = function` in the constructor, `X.prototype.y = …`) and `X.y = function` are read (`JSDef.member`: named after the owner, `PostItem.Skeleton`, but not a name in scope, and it sees the names of the place it is written, `JSDef.lexical`); `const f = wrap(function …)` keeps the inner function (`wrapped-function`, likely). `JSResolver.resolve_more` runs only where the older resolution found nothing, so no link it made changes: values bound in a scope (`const app = express()`, `db = require('lib')`) (`library-value`, `module-value`), results of library calls (`ext:<lib>.<f>().<m>`, `library-result`), Express handler parameters by position (`req`, `res`, `next`: `express-param`, only where the nearest `package.json` depends on express), written TS parameter types (`param-type`), DOM and `fetch` results (`builtin-value`, counted in `g.builtin_calls`). A library or built-in label is withheld (`JSResolver.may_be_own`, reason `library-or-repo`) where the function may be the repo's own: the Walker records functions the code puts on an object that is not its own (`JSModule.put`: `schema.statics.x = function`, `res.fail = function`, `schema.methods = {…}`, `schema.method('x', fn)`, `Object.assign(obj, {…})`; `given`: `{ methods: {…} }`), and `JSResolver.own_names` sorts them by owner (`_owner_kind`: a library's object of a known kind, a built-in type, an object it cannot name, or the repo's own function/class/module/plain object, which never counts). A direct member of Express's `req`/`res`/app/router, of a written type, of `new LibraryClass()` or of a built-in value is doubted only when the repo puts that name on that kind of object; any other library value also when a repo class with that method was handed to the library calls it came from (`JSRef.args`, `JSModule.value_args`: `getRepository(User).findOne()`), and what hangs on `req`/`res` (`req.user.can()`) when any repo class has that method (`EVERYDAY_MEMBERS` aside). A route's `middleware` list keeps the name either way. `window.App.init()` (a property of the global object that is not the browser's or Node's own name) is unresolved `global-property`, not a built-in (`JSResolver.global_doubt`). An import that finds no file names a file of the project, never a library, when it is a relative, `@/`, `~/` or `#` path (`FILE_SPEC`) or a path alias of the nearest tsconfig/jsconfig that points at a project path (`SpecResolver.lost`: `"contentlayer/generated": ["./.contentlayer/generated"]`, a generated folder that is not committed; not a catch-all `*`, not a target inside `node_modules`, and not when the alias covers a package the nearest `package.json` depends on: the package's own name, or `@acme/published` under `@acme/*`): the map keeps the older `ext:` edge, the inventory says `missing-module`, and nothing is built on the value (`JSResolver.unread`). Express routers: `app.use('/api', router)` (a variable, `require('./r')`, a factory given the router `require('./r')(express.Router())`, or a factory that returns its module's router: `JSModule.returns`) gives the router's routes the full prefix; the handlers and middleware named in `router.verb(path, mw…, handler)`, and in verbs hung on `router.route(path)`, get `route-handler` / `middleware` edges (resolved when named straight from a module, likely when reached through a worked-out value or type) and `entry["middleware"]`, which the login check reads (`websec.route_auth_sign`: the function's own name, i.e. what follows the last `.` and `/`, so `./auth/rate-limit` is not a login check and `./mw/guards.requireLogin` is). A route is an entry only on a function of the repo: when its handler is a library's function, or comes from a file that is not there, no node is marked (a library node is never an entry point) and the handed record says `external` or `missing-module`.

To add a rule (either language): write a failing test with a tiny repo via `_write()`
(`tests/test_frontend.py` for Python, `tests/test_fullstack.py` for JS/bridge/web security), give the
edge a distinct `via`, run `bench/run_bench.py`, and check the numbers before choosing its confidence.

## Known gaps

* Go: no runtime tracing, no `go vet`/gosec/govulncheck yet (only the `LG-*` patterns); generics, function values
  stored in variables, and methods promoted through more than one embedding level are unresolved; a call on a
  `map`/`chan`/closure result is counted, not guessed. Confidence levels are not yet backed by a Go benchmark.
* Rust: no runtime tracing, no cargo-audit/clippy yet (only the `LR-*` patterns); macros other than `format!` and
  `routes!` are opaque (a route declared inside a macro is missed); closures stored in variables, trait objects
  built through generic constructors, and associated types are unresolved; `impl Trait for X` matching is by trait
  name, not path. Confidence levels are not yet backed by a Rust benchmark.
* Kotlin: no runtime tracing; extension functions, scope-function receivers (`with(x) { f() }`, `apply`), and calls
  on a lambda's `it` are unresolved; Ktor `routing { get("/p") { } }` routes are not entry points yet (Spring's are);
  types are matched by simple name. Confidence levels are not yet backed by a Kotlin benchmark.
* Flutter/Dart: no runtime tracing; `dynamic`/`var` receivers from library calls, generics, extension methods on library
  types, `Provider`/`Riverpod`/`Bloc` lookups (`context.read<T>()`) and callbacks passed as closures to library widgets
  are unresolved; a screen opened only through a route name string built at run time is found only if it is called
  `…Screen`/`…Page`; `pubspec` libraries are not audited yet.
* PHP: no runtime tracing; untyped variables and properties (`$x = $this->make()` without a written return type,
  `$app->make(Repo::class)`, service containers, facades backed by repo classes), magic methods (`__call`, Eloquent
  scopes and relations), `$this->{$name}()` and string-built callables are unresolved; Blade/Twig templates are not
  mapped (only `{!! !!}` is checked); routes registered through a helper, a loop or `Route::controller()` are missed;
  a plain page's URL assumes the web root is `public/`/`htdocs/`/`www/` or the repo root. Confidence levels are not yet
  backed by a PHP benchmark.
* C/C++: no runtime tracing, no library audit (Conan/vcpkg/system packages are not checked); macros are opaque except the route
  macros named above (a function called only through a macro is missed); templates are looked through by name, overloads share
  a node, virtual calls land on the static type's method (no `possible` fan-out to overrides yet), function pointers and
  callbacks stored in variables are unresolved; free functions with the same name in two programs share a node (except
  `main`); `#include` is not followed, so a type is matched by name across the repo; the input check follows values inside one
  function only. Confidence levels are not yet backed by a C/C++ benchmark.
* Ruby: no runtime tracing; types come only from `X.new`, Active Record finders and `@x = X.new` (method return values,
  `let`/`subject` in specs, dependency injection and duck-typed parameters are unresolved); metaprogramming
  (`define_method`, `method_missing`, `send(:name)`, concerns' `included do` blocks), Active Record associations
  (`note.user.name`) and scopes, Rails engines/`draw(:file)` route files, Grape/Roda/Hanami routes, `rescue_from`, and
  ERB/Haml templates beyond the `LB-XSS-RAW` line check are not mapped; Gemfile.lock gems pulled in only by dev/test
  gems are still checked. Confidence levels are not yet backed by a Ruby benchmark.
* C#: no runtime tracing, no NuGet audit yet (only the `LC-*` patterns); types are matched by simple name inside the
  usings' namespaces; extension methods, LINQ lambdas' receivers, generics (`List<Note>` is `List`), `dynamic`, DI
  registrations (`AddSingleton<IRepo, SqlRepo>()` is not read: an interface field fans out to every implementation),
  Razor `.cshtml`/`.razor` code and XAML `Clicked="OnSave"` bindings are not mapped (a page's `…Clicked` handler is an

  the ones they pull in;

Python: a subscripted repo base (`class Notes(Repo[Note])`) is not followed into `Repo`; an absolute import of a project file that is not there (`from app.gen import x`) is still read as a library (only relative imports are certain), and so is a library module that shares its name with a repo file the suffix index maps it to (`from celery import shared_task` beside `proj/celery.py`: `repo-variable`). Library labels are withheld on the safe side, so some true library calls stay unresolved (`library-or-repo`): `self.client.get()` in a Django test when any repo class has a `get`, `self.headers.get()` in Lantern's own server. They can still be wrong where Lantern sees no sign of the project's function: a plain object with functions handed to a library and read back (`useStore.getState().inc()`, a `useImperativeHandle` handle), a class the library got somewhere else than in the calls the value came from (a DI container asked by a string name), a helper that decorates `res` through a parameter with another name, a library class patched from Python (`Lib.method = fn`), and an everyday name on a Python call result (`copy.copy(cart).update()`). `window.scroll()`-style calls are built-ins only for the names in `JS_BUILTINS` and `WINDOW_MEMBERS`; anything else on `window` is `global-property`. `Graph.call_sites()` grows where newly linked JS test-file calls and route-handler/middleware edges add edge lines, so compare stages on the inventory, whose denominator does not move.
* Test sandbox (stage 7): what it promises is what this system's sandbox is designed to set up. A Linux kernel with no Landlock, macOS and Windows have fewer walls and tests still run there (a non-Python program the tests start can then write where the user can, and use the network); only a restriction that exists and fails stops the tests. macOS has no supervisor: the process group is ended, a process that left it survives. On Linux with Landlock below ABI 6 and Lantern not root, a test can signal its own launcher, and what left the session before the launcher was killed survives. A Docker container whose tests never end outlives a Lantern killed with `-9`. A Lantern that is killed, or whose tidy-up takes longer than the 30 seconds the closing app waits, leaves the sandbox's temp folder (the copy of the project) where it is. A hostile test can print the launcher's marker and end with 119, and is then reported as not run (Lantern's sentence, nothing merged), or print the launcher's "could not be ended" line and be reported as having left something. The Windows Job Object is tried against Windows itself only by four tests of CI's Windows job. A sandbox temp folder that could not be deleted is named in the log and written down; it is deleted when the next test run on this computer starts, not before. A test that asks a program already running on the computer to start something for it (a service manager, the task scheduler, WMI, a container daemon) is not followed: that is neither beneath the launcher nor inside the job. The app's terminal drawer has no Stop button (its `trace` job can be stopped through the route).
* Clean-up (stage 7): the cloud service removes only what carries its own name and mark, so two kinds of leftovers from before 2026-11-10 are counted for the owner (`left_alone`) and never removed by it: a work folder a cut-off run of an older version left (no mark), and a results folder no run points at (a delete that failed then left no record); `docs/deploy.md` says how to remove them by hand. Removing what is written down is tried at each start and each hour the service is awake, not in between; the health page turns `behind` only after 24 hours. A failed pass that leaves nothing overdue is in the owner's statistics and the log, not in the health word. The service takes only plain files from a finished step (`worker._take`), which closes the way through a link; a step that was taken over can still read whatever its user can read and write it into its own report (Landlock limits writing and the network, not reading, and the cloud image runs the service and its steps as one user): `docs/audit/THREAT_MODEL.md`, open risk 0. Nothing known runs a stranger's code inside a step since a folder's own git settings are no longer obeyed (`lantern/gitfacts.py`). Explanations written before the service is shut down in the middle, or before the step ends with an error other than the time limit, are not kept. On a person's computer `remove_tree` and the sandbox say what stayed, and only the sandbox's temp folder is retried (the next test run); a clone folder that could not be removed after a failed clone is named in the error and left to the person. On Windows removal goes by path (`shutil.rmtree`, which looks at each folder before it enters it): a folder swapped for a link between that look and the step is not caught, and a folder nested deeper than Python recurses stays, with the reason said.
* Dependency audits need exact versions: Python ranges without a lock file, pnpm/yarn/bun lock files, and Gradle
  versions with `+`, ranges or unresolved variables are reported as not checked, and so are a Composer library
  installed from a branch, a Pipfile.lock entry from a link or a folder and a lock entry with no version (counted,
  with the first five as examples). `npm audit` reads package-lock.json itself, so Lantern does not look at its
  entries. An audit that is skipped (`--offline`, tool not installed) names the odd entries of a dependency file only
  when nothing in the files could be used; otherwise its record says it was skipped and the next run that asks names
  them. A well-formed name of a package that does not exist is asked about as written. Poetry's exact pin
  (`flask = "2.0.1"`) is still listed as not bounded by readiness's `deps-pinned`.
* Project files and earlier results (stage 7): an odd part of a manifest outside its dependency sections (an alias,
  a script, a notebook cell) is passed over without a line in the report. The commands about a finished run
  (`lantern report`, `evidence`, `explain`, `verify`, `export`, the connector's tools) still stop on a result file
  they cannot read, on purpose; the app, Ask Lantern and the Learn tab have readers of their own that
  `bench/manifests.py` does not cover. A result file of the right shape that Lantern did not write is taken as its
  own. Windows has no `O_NOFOLLOW`, so there a result file swapped for a link between Lantern's look and its read is
  read. The sweep holds 21 kinds of file; a reader added later is covered only when its file is added to `KINDS`.
  Writing: a results folder that is a link inside the project is refused also when the person made the link
  themselves (`--out FOLDER` names another place; the app always uses `PATH/.lantern` and has no such choice). A
  link put in place between Lantern's look at the results folder and its write is not seen. A run killed in the
  middle of a write leaves a file `.<name>.<16 hex>.part` beside the result file; nothing reads it and nothing
  removes it. The Windows way of `results.write` (a junction or a link removed as itself, then the replace) is
  tried only by two tests of CI's Windows job.
* Files by name, results read back (stage 7): `bench/links.py` was run with all six states under Python 3.13 and 3.11
  and with the state "a link to itself" under 3.12 (the first push had 3.13 and that one state only, and GitHub's tests
  under 3.11 then failed on an iPhone app's settings file: `bench/links_results.md`). It sees a read only when what the file holds changes a
  result file; a reader whose file changes nothing in the samples is covered only by the look for openers
  (`test_no_file_is_opened_any_other_way`), which knows `open`, `os.open`, `read_text`, `read_bytes` and `.open` in
  `lantern/`, not a library or a tool that is handed a path and opens it itself. Of the tools, Bandit and `npm audit`
  are told what to leave out; gitleaks finds its files itself and was not measured (it is not installed where the
  sweep ran; Lantern does not ask it to follow links). The question (`inside_repo`) and the open are two steps: a
  link put in place between them is read (that takes another program writing in the project at that moment).
  Whether a name is a folder is still asked the plain way in places (`sandbox.detect`: `tests/`), so a folder link
  that leads out counts as a folder; no file is read through it. "Seen running" is what the project's own tests
  wrote down: `trace.well_formed` keeps only rows of the recorder's shape, and a test program can still write rows
  for calls between two functions of the map that never happened (marked seen running, or added as `runtime-only`;
  it cannot add a function, and a call takes no finding away). The cloud service's own readers of a run's results were not changed (its results
  folder holds only what `worker._take` copied as plain files), and `worker.explain` still rewrites `repo_root`
  before `lantern explain`, which no longer reads it. The sweep is POSIX only: the Windows side of these readers
  (`results.plain` without `O_NOFOLLOW`, junctions) is tried by the tests of `tests/test_links_out.py` and
  `tests/test_results_folder.py` that CI's Windows job runs, not by a sweep.
* "Uses input" follows assignments inside one function, in order (parameters, request data, and variables set
  from them), not across functions, branches, or loops. Parameters are read from the signature per language (Java/C#:
  the last identifier of each `Type name`; Kotlin and Swift: the name before each `:`, and `$x`/`${x}`/`\(x)` string
  templates count as using `x`; Go: without the receiver; Rust: the pattern before `:`, unwrapping
  `State(x)`/`Path(x)`/`Json(x)`); request data patterns cover Flask/Django/Express/Next, Go's net/http, gin, echo,
  fiber and chi, and Java servlets. A value that arrives through another function's return
  value is missed; a parameter that is always a constant is over-ranked. A plain `x = <safe value>` at the same
  block level clears `x`; a default inside an `if` (`if not x: x = "ls"`) does not, and neither does `x += ...`,
  so a value that is always replaced inside a branch stays ranked critical (the safe direction).
* The login check (`LW-AUTH-MISSING`, protection `route-auth`) reads names, not meaning: strings, comments, request
  data and the names that hold it are blanked first; an auth word must be a whole segment of a name (`get_token`,
  `has_permission`, `protectedProcedure`; not `tokenize`, `load_permissions`, `protect_zone`; `websec.auth_word`;
  `verify` only with the caller as its object: `verify_token`, `verify_session`, `verify_api_key`, not `verify_payment`) and
  counts only as a call or an attribute, a parameter
  only through a dependency, type, injected header or cookie, or caller name; a user lookup counts only when its
  argument identifies the caller (a token, session or request parameter, a `_by_token` lookup, or no argument at all,
  which is taken as "the session", deliberately) and is otherwise at most `check`, which includes a token read from
  the request body. Missed: a check hidden behind a helper with a neutral name (`load()`), or a bare local flag
  (`ok = role == "admin"`). Both land on `add`/`check`, the safe side.
* Git facts (`lantern/gitfacts.py`): no commit is reported, with a `note`, for a `.git` that is a link, for a `.git` file whose target does not name the folder back (`git init --separate-git-dir`), for refs kept in the reftable form, and for a bare repository; files count as changed, with a note, when git cannot compare them (an index or objects folder that is a link, a submodule whose git folder is not read, submodules nested more than five deep). A filter or a submodule-ignore rule that only the repository's own settings define is not applied, so a file can count as changed. git still reads the project's index, objects (and the other object folders the repository names) and `.gitattributes`, as for any cloned repository. Whose git folder it is: the folder asked about is read whoever owns it (git itself would refuse it when it is another user's; nothing in it is obeyed, but git reads its index and objects), and only what lies outside it falls under git's rule. Where Lantern differs from git there, it is stricter or follows the person's own settings: a Windows home folder that the system owns is not taken for the person's (git for Windows takes it), so a repository kept in the home folder itself gives no commit to a folder beneath it for a person who is not an administrator, until `safe.directory` names it; the folder a linked worktree shares is looked at too; `safe.directory` is read as git reads it since 2.46 (`/folder/*`, `.`) whatever git is installed, compared without regard to upper and lower case on Windows, an entry that begins `%(prefix)/` is passed over, and an entry stands for the folder it names however that folder is spelled (a link, a Windows short name such as `C:/Users/RUNNER~1/...`), where git for Windows 2.56 leaves a short name in a `/folder/*` entry as written and then does not match it (the first GitHub run of this rule on Windows failed on that one comparison with git, 1 failed, 1124 passed, 68 skipped: a test that asks git about such an entry writes it with the folder's real name). The Windows calls are tried against a stand-in everywhere and against Windows itself only by two tests of CI's Windows job, whose sign-in is an elevated administrator: the path for an administrator who is not elevated has only the stand-in. The test with real other owners needs root and runs nowhere in CI (there the rule is tried through stand-ins for the owner and the user, and through git's own switch `GIT_TEST_ASSUME_DIFFERENT_OWNER`). A folder none of whose files the repository above keeps is still reported with that repository's commit and no uncommitted changes when the repository is the person's own (a new folder not added yet, an ignored one): only files git keeps track of count as changed, as with git. `GIT_DISCOVERY_ACROSS_FILESYSTEM` is not read. The settings file is read the way git reads it since 2.45 (a tab inside a value stays a tab; older git made each blank inside a value a space), and a developer's git can be older than CI's (2.43 against 2.56 on 2026-11-10: the first GitHub run of `tests/test_gitfacts.py` failed on that one value), so a test that compares with git's own output has to hold for both. Lantern's own clones under `LANTERN_HOME/repos` are still updated with plain git (their `.git` was written by Lantern's own `git clone`), and so is Lantern's own checkout (`evidence.engine_ref`).
* The report embeds source by default; `--privacy structure` omits it.
* Model explanations exist only for selected nodes (entry points + 3 levels, capped at 40 by default); every other
  function shows lenses the viewer builds from the map (`mapRecord` in `report.html`: facts only, byline says so).

## Conventions

* Python 3.11+, standard library plus tree-sitter grammars; no network calls except model providers and the dependency
  audits (skippable with `--offline`).
* A library a new test needs goes in the `dev` extra in `pyproject.toml` and, pinned, in `requirements-lock.txt`
  (its header says how to refresh it; put the hand-written header back afterwards). CI installs `.[scan,dev]` and
  fails a run in which a test was skipped for a missing library; never work round that with a skip.
* Tests and benchmarks never reach a real model provider or the internet and never see the developer's keys
  (`tools/netguard/`, `tests/conftest.py`). A new test gets a stand-in (`FixtureProvider`, `tools/fake_model.py`, a
  server on 127.0.0.1); a new benchmark's `main` starts with `netguard.begin(allow=[the hosts it must reach])` and ends
  with `netguard.end(guard)`, and its file is added to `BENCHMARKS` in `tests/test_isolation.py` (a benchmark that is
  not listed there fails `test_no_benchmark_is_left_out`); anything that measures a real model goes through
  `bench/live.py`'s `gate`. Never add a
  default model or a fallback to whatever key the shell holds in a script.
* Always pass `encoding="utf-8"` to file reads/writes and `subprocess.run(text=True)`, and build repo-relative paths with
  `.as_posix()`: Windows CI runs with the system code page and backslash paths.
* Open a file of the analyzed project only with `python_frontend.project_text(p, repo[, limit])` or `project_bytes`:
  they ask `inside_repo(p, repo)`, which is True only for a plain file, or a link to one, that lies inside the project by
  whatever folders it is reached (not a link that leads out, not a file behind a folder that is such a link or junction,
  not a pipe or a folder under a file's name, not a path that leaves through `..` or starts at the top of the disk), and
  raise FileNotFoundError for anything else, so a reader that passes a missing file over passes these over too. That goes
  for a file found by its name (`package.json`, `go.mod`, a notebook, `lantern-narratives.md`) and for a path kept in an
  earlier result (a function's `file` in graph.json). Where a reader first asks whether a file is there, it asks
  `inside_repo`, not `exists()` or `is_file()`: those follow a link, and the results then tell whether a path outside the
  project exists. A look for a name (`glob`, `rglob`) is no such question either: for an exact name it finds a link only
  when something is at its end before Python 3.12 and whatever is at its end from 3.12 on, so a finder that names what
  it found asks `inside_repo` before it names it (`ios.find_apps`, `learn.check`). A tool that finds its files itself is told what to leave out and has nothing taken from such a file
  (`security.run_bandit`: `_not_the_projects`, `_only`, the record's `exclusions`; `depaudit.run_npm_audit` counts a lock
  file that is a link out as none). A result file is read back only with `results.plain` / `text` / `table`, and a saved
  map is loaded with the folder the caller was given (`Graph.load(path, repo)`), never the one the file names.
  `tests/test_project_files.py::test_no_file_is_opened_any_other_way` reads every module of `lantern/` and fails on an
  `open`, `read_text` or `read_bytes` outside the openers; a place that opens a file of Lantern's own (a template, a file
  in `LANTERN_HOME`) is added to its `OWN_FILES` with the reason. Sweep: `python bench/links.py --jobs 4` (not in CI; run it
  after adding a reader, under the oldest Python Lantern supports as well as the newest, and put a file that is looked for by its name into its `EXTRA` when no sample holds one). Tests:
  `tests/test_links_out.py`, `tests/test_project_files.py`.
* Files in `.lantern/` live in the analyzed folder and may be planted: the server rebuilds every page from our templates,
  and anything rendered from them must be escaped. A file is written there, and anywhere else in a project, only with
  `results.write` (never `write_text` or `open(..., "w")`, which follow a planted link), and the folder comes from
  `pipeline.out_dir`.
* Keep `report.html` a single self-contained file that works offline and on a phone.
* UI: the design is the Claude Design handoff (`Lantern_UI_mockups`: tokens, shared chrome, backdrop, Ask Lantern, ten
  screens in Simple/Advanced). The design tokens at the top of `app.html`, `report.html` and `evidence.py` are one set
  (accent teal `#0F7B74`/`#4FC3BA`, DM Sans / Lora / JetBrains Mono with system fallbacks; the report stays offline and
  never loads fonts from the network); change all three together. `app.html` has the backdrop (`#bg`, three drifting
  SVG layers, `settings.backdrop` off/subtle/bold, quiet on project screens; `report.html` draws the same geometry as
  `.backdrop` when opened on its own, `LANTERN_LIVE.backdrop`, and none inside a frame, where it is transparent), the Simple/Advanced toggle
  (`settings.view_mode`, phones Simple only) and the Ask Lantern pill/window (`#ask`).
  Status colors (good/warning/serious/critical) mean risk or results only and always sit beside a word or icon.
* Plain language in user-facing text; technical detail lives in Lens 1, `via`, and `detail`.
* Never commit real-looking secrets in fixtures (GitHub push protection); build them at test time.
* The connector and the plugin seams never get a way to create, dismiss, close or re-rank a finding. New MCP tools
  are read-only or re-run the analysis; new seams are data (patterns, endpoints, exports), not code.
